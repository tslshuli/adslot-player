本文档整理自日常运维过程中的巡检项、判读标准与处置流程，适用于机房自建及云上独立部署的 Linux 服务器。内容以可执行命令和明确阈值为主，便于交接与复用。

文档中的命令默认以 root 或具备 sudo 权限的账号执行。涉及生产环境的操作（重启服务、清理文件、调整内核参数）请先在测试环境验证，并保留操作记录。

1 适用范围与约定

1.1 适用对象

  • 操作系统：CentOS 7 / Rocky Linux 8+ / Ubuntu 20.04+
  • 部署形态：单机部署、主备部署、容器化部署（Docker / Podman）
  • 不覆盖：Kubernetes 集群运维、云厂商托管数据库的底层维护

1.2 术语约定

术语 含义
巡检 按固定周期对系统状态做只读检查，不做任何变更
阈值 触发人工介入的指标上限，本文档中的数值为默认建议值
处置 对异常项做变更操作，须记录时间、操作人、变更内容

2 巡检周期与责任划分

巡检分日常、周度、月度三档。日常项只做读取和记录，发现问题走告警流程；周度、月度项包含例行清理与验证，可以安排在业务低峰期执行。

巡检项 周期 执行方式 记录位置
硬件与负载状态 每日 手动 / 脚本 巡检表
磁盘与 inode 每日 脚本采集 监控平台
服务进程与端口 每日 脚本采集 监控平台
日志切割与清理 每周 手动确认 变更单
系统补丁评估 每月 手动 变更单
备份可恢复性验证 每月 实际恢复一次 演练记录
备份"看起来成功"和"真的能恢复"是两件事。每月至少挑一台机器做一次完整恢复，恢复不出来等于没备份。

3 系统层巡检

3.1 负载与 CPU

uptime
top -bn1 | head -20
mpstat -P ALL 1 3      # 需要 sysstat

判读标准：load average 的 1 分钟值连续 5 分钟超过 CPU 核数的 1.5 倍，视为异常。注意 15 分钟值仍然很高但 1 分钟值已回落的情况，通常说明压力刚过去，先观察不要立即处置。

若 %sy（内核态）持续偏高，优先排查中断是否集中在单核；若 %wa（IO 等待）偏高，转去看磁盘章节。

3.2 内存

free -h
vmstat 1 5

看 available 而不是 free。free 数值低是正常现象，Linux 会主动用空闲内存做缓存。available 低于总内存的 10% 时，结合 vmstat 的 si/so 两列判断：两列长期非零说明已经在换页，需要处理。

3.3 磁盘空间

df -hT
du -sh /var/* 2>/dev/null | sort -rh | head -10
lsof +L1 | head -20      # 已删除但被占用的文件

使用率 80% 预警，90% 处理。常见的大文件位置如下，清理前确认是否还在写入。

路径 常见内容 处理方式
/var/log 系统与应用日志 配 logrotate，确认切割后再删
/var/lib/docker 镜像与容器层 prune 无标签镜像
/tmp 临时文件 按 mtime 清理，注意挂载类型
/home/*/.cache 用户缓存 确认用户无任务后清理

df 显示已满但 du 统计不出来，说明有进程持有已删除的文件句柄，用 lsof +L1 定位，重启对应进程即可释放。

3.4 inode 使用率

df -i

小文件多的场景（邮件队列、会话文件、临时分片）容易出现空间还有、inode 先满。典型表现是新文件无法创建但 df -h 看着很正常。

4 服务层巡检

4.1 服务状态

systemctl --failed
systemctl status nginx --no-pager
systemctl list-units --type=service --state=running

4.2 端口与连接

ss -tlnp
ss -s
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn | head

重点看 TIME-WAIT 与 CLOSE-WAIT 的数量。前者偏高通常是短连接过多，可以调内核参数缓解；后者偏高说明对端已关闭但本端没释放，多半是应用没有正确关闭连接，要从代码侧处理。

4.3 文件句柄

cat /proc/sys/fs/file-nr
ulimit -n
ls /proc/<pid>/fd | wc -l

第一列是已分配句柄数，接近上限时新连接会被拒绝。调整 LimitNOFILE 后必须重启对应服务才生效，systemctl reload 不够。

5 日志检查

journalctl -p err --since "24 hours ago"
tail -n 200 /var/log/nginx/error.log
awk '$9 ~ /^5/ {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

最后一条用于统计 5xx 按 URL 聚合，能快速定位是全局故障还是单个接口的问题。日志量大的机器建议先 tail 再处理，避免 cat 大文件拖慢机器。

logrotate 的最小可用配置：

/var/log/app/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}

copytruncate 适用于程序不支持重开日志文件句柄的情况，代价是切割瞬间可能丢少量日志。支持 SIGHUP 的程序应该改用 create 配合 postrotate。

6 常见故障处置

下表按现象索引。处置列的步骤按顺序执行，前一步没解决问题再做下一步。

现象 可能原因 处置
磁盘满，写入失败 日志未切割 / 镜像堆积 lsof 查句柄 → 清理 → 配 logrotate
服务在但无响应 进程假死、死锁 抓栈 → 重启 → 保留现场
CPU 持续 100% 死循环、异常进程 top 定位 → 确认归属 → 处理
新连接被拒绝 文件句柄或端口耗尽 查 file-nr / ulimit → 调整 → 重启
时间漂移 NTP 未同步 chronyc sources → 重新同步
磁盘 IO 高 大量小文件读写、swap iostat 定位设备 → 查进程 io

6.1 服务假死的处理顺序

不要上来就重启。先留证据：

ps -eo pid,ppid,stat,wchan,cmd --sort=-%cpu | head -20
cat /proc/<pid>/stack          # 需要 root
gdb -p <pid> -batch -ex "thread apply all bt" 2>/dev/null | head -100

拿到栈之后再重启。没有栈的故障复盘会变成猜谜，同样的问题会反复出现。

7 备份与恢复

遵循 3-2-1 原则：三份副本、两种介质、一份异地。落地时至少保证有一份不在同一台物理机上。

rsync -avz --delete --exclude='*.tmp' \
      /data/ backup@10.0.0.12:/backup/data/
备份对象 频率 保留 验证方式
业务数据目录 每日 30 天 每月恢复一次
数据库全量 每日 14 天 导入测试库校验
配置文件 变更时 永久 版本库对比
系统镜像 每月 3 个版本 试启动
恢复演练要真的恢复到一台干净的机器上。在同机器上解压看文件在不在，验证不了依赖、权限和启动顺序。

9 文档维护

本文档随实际处置经验更新。新增故障案例时，按"现象—原因—处置—验证"四段写，不要只写结论，否则半年后没人看得懂当时为什么这么处理。

阈值部分（80%、90%、1.5 倍核数）是通用建议值，实际部署应按业务特点调整。业务侧对延迟敏感的场景，IO 与连接数的阈值应当收紧。
