本文整理数据库备份的选型、执行与恢复流程，重点是"恢复"而不是"备份"。多数事故不是因为没备份，而是因为需要恢复时才发现备份不可用、或者不知道恢复到哪个时间点。

文中命令以 MySQL / PostgreSQL 为例，其他数据库思路一致。生产环境的恢复操作必须在隔离环境先演练，确认无误后再动线上。

1 适用范围与前提

1.1 适用对象

  • 关系型数据库：MySQL 5.7+ / 8.0、PostgreSQL 12+
  • 部署形态：单机、主从、云托管实例（托管实例至少要做逻辑导出，不能只依赖厂商快照）
  • 数据量：单库 500GB 以内可以走逻辑备份；再大要考虑物理备份或快照

1.2 前提条件

  • 备份账号具备 SELECT、RELOAD、LOCK TABLES（MySQL）或 REPLICATION 权限
  • 备份目录所在磁盘剩余空间不少于数据量的 3 倍
  • 已开启 binlog / WAL 归档，且保留期覆盖最长恢复需求
没有验证过恢复的备份，只能算"有文件"，不能算"有备份"。这句话听着像口号，但每年都有团队栽在上面。

2 备份类型与选型

类型 速度 恢复粒度 适用场景
逻辑全量（dump） 慢 库 / 表 中小库、跨版本迁移
物理全量（xtrabackup） 快 实例 大库、快速恢复
binlog / WAL 实时 时间点 误删恢复、主从同步
存储快照 极快 整盘 云环境、大版本变更前

实际部署通常是组合使用：每日全量 + 实时 binlog，恢复时先还原最近一次全量，再重放 binlog 到目标时间点。

3 全量备份

3.1 MySQL 逻辑备份

mysqldump -u backup -p \
  --single-transaction \
  --quick \
  --routines --triggers --events \
  --set-gtid-purged=OFF \
  --databases app_db \
  | gzip > /backup/mysql/app_db_$(date +%F_%H%M).sql.gz

几个参数不能省：--single-transaction 保证 InnoDB 表的一致性快照且不锁表；--quick 避免把大表一次性读进内存；--routines --triggers --events 否则存储过程、触发器会丢。

--set-gtid-purged=OFF 是为了让导出的文件能在另一个实例上直接导入。如果要用于搭建从库，则应保留 GTID 信息。

3.2 PostgreSQL 逻辑备份

pg_dump -U backup -Fc -Z 6 -f /backup/pg/app_db_$(date +%F).dump app_db

-Fc 输出自定义格式，支持并行恢复与选择性还原；-Z 6 压缩级别。纯 SQL 文本格式（-Fp）便于人工查看，但恢复慢、不支持并行。

4 增量：binlog 与 WAL

全量备份只能恢复到备份那一刻。要恢复到"误删之前 1 分钟"，必须依赖日志。

# 确认 binlog 已开启
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';   # 应为 ROW

# 查看当前写入位置
SHOW MASTER STATUS;

binlog_format 必须是 ROW。用 STATEMENT 格式时，某些函数（如 NOW()、UUID()）会导致主从不一致，恢复重放也可能出错。

日志保留时长由 binlog_expire_logs_seconds 控制，默认 30 天。如果业务要求能回溯更久，要么调大，要么定期归档到对象存储。

5 存储与保留

遵循 3-2-1：三份副本、两种介质、一份异地。落地时至少保证一份不在同一台物理机上、不在同一个可用区。

备份对象 频率 保留 存放位置
全量逻辑备份 每日 02:00 30 天 本地 + 异地对象存储
binlog 实时 14 天 本地磁盘
周度归档 每周日 6 个月 异地对象存储
变更前快照 按需 变更后 7 天 云盘快照

注意"保留 30 天"不等于"能恢复 30 天前"。如果有备份失败未告警，中间某天缺失，恢复链就断了。所以必须有备份成功率的监控。

6 备份有效性验证

验证分三层，从浅到深，建议每月至少做到第二层。

层级 做法 能发现的问题
文件级 检查文件大小、gzip 完整性 文件截断、空文件
可导入 导入测试库，统计表数量与行数 语法不兼容、权限缺失、字符集错乱
可恢复 走完整恢复流程，业务方抽查数据 丢失索引、触发器、外键、序列值 
# 快速检查 gzip 完整性
gzip -t /backup/mysql/app_db_2026-11-13_0200.sql.gz && echo OK

# 统计备份内的表数量（MySQL 逻辑备份）
zcat app_db_2026-11-13_0200.sql.gz | grep -c 'CREATE TABLE'

7 恢复流程

7.1 误删单表

不要直接在生产库上操作。先恢复到临时实例，再从临时实例导出目标表覆盖回生产。

# 1. 解出全量备份到临时实例
gunzip -c app_db_2026-11-13.sql.gz | mysql -h temp-host -u root -p

# 2. 重放 binlog 到误删前的时间点
mysqlbinlog --stop-datetime="2026-11-14 09:41:00" \
  /var/lib/mysql/mysql-bin.000123 \
  | mysql -h temp-host -u root -p

# 3. 单表导出并回写
mysqldump -h temp-host -u root -p app_db orders > orders_fix.sql
mysql -u root -p app_db < orders_fix.sql

7.2 整库误删

先确认没有写入正在进行（停应用或切只读），否则恢复过程中产生的新数据会与备份冲突。恢复完成后再放开写入，并核对自增 ID 与序列是否连续。

7.3 恢复到指定时间点

关键在 --stop-datetime 的取值。判断依据是业务侧提供的最后一条正常数据的时间戳，而不是"你觉得大概什么时候删的"。宁可选晚一点、丢掉少量数据，也不要选早（会丢更多）。

恢复前把当前库整体再备份一份，哪怕它已经是坏的。恢复过程中如果判断失误，这份"坏备份"是唯一能回到起点的东西。

8 常见问题

现象 原因 处理
导入报字符集错误 导出与导入端默认字符集不一致 显式指定 --default-character-set=utf8mb4
恢复后自增 ID 冲突 未恢复 AUTO_INCREMENT 值 导入后 ALTER TABLE ... AUTO_INCREMENT=
备份文件明显偏小 dump 中断但管道未报错 检查 PIPESTATUS，不要只看最后一行
binlog 重放报 duplicate entry 全量备份点与 binlog 起点不匹配 核对 SHOW MASTER STATUS 记录的位点
恢复极慢 逐条 INSERT、未关自动提交 导入时 SET autocommit=0 并分批 commit

9 变更与文档维护

本文档随实际演练结果更新。每次做恢复演练后，把遇到的问题补进"常见问题"表；每次调整备份策略，同步更新第 5 节的保留表。

建议每季度完整走一次恢复演练，选一台与生产同版本的干净机器，从零开始恢复，记录耗时。这个耗时是事故时的预期恢复时间，比任何承诺都可靠。
