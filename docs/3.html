网络变更的风险不在"改什么"，而在"改完之后影响了谁"。一条看起来只影响某个 VLAN 的 ACL，可能让整栋楼的打印机连不上。本文把变更拆成可检查的步骤，目的是让每一次改动都可以回退、可以复盘。

适用于交换机、路由器、防火墙的配置变更。云上安全组与路由表的调整同样参考本文流程。

1 目的与适用范围

规范网络设备变更的申请、审批、实施与验证流程，降低因配置错误导致的业务中断，保证每次变更都有据可查、有路可退。

  • 覆盖设备：核心交换机、接入交换机、出口路由器、硬件防火墙
  • 覆盖操作：VLAN 调整、ACL 变更、路由策略、端口配置、固件升级
  • 不覆盖：新设备上线（走独立的项目流程）、纯监控采样配置

2 变更分级

分级决定审批人与实施时间窗口。定级的核心是"最坏情况下影响多少人"，不是"改几行命令"。

级别 判定标准 审批 时间窗口
A 级（重大） 影响核心链路、出口、跨机房互通 网络负责人 + 业务负责人 夜间 22:00 后
B 级（常规） 影响单个楼层或单个业务系统 网络负责人 业务低峰期
C 级（轻微） 不影响转发，如描述、备注、监控采样 组长 工作时间内

定级有争议时，按高一级处理。把 A 级当 B 级做，代价通常是通宵。

3 变更申请要素

一份可以执行的变更单至少包含六项，缺任何一项都应该退回补充。

要素 要求
变更内容 具体配置差异，以"改前 / 改后"两段配置呈现
影响范围 涉及哪台设备、哪些网段、哪些业务系统
实施时间 起止时间，含验证时间
回滚方案 具体命令，不是"恢复原配置"这种话
验证方法 从哪台机器、用什么命令、看到什么算成功
失败预案 回滚后仍不通时的升级路径与联系人
"回滚方案：恢复原配置"——这句话等于没有回滚方案。真出事的时候，没人能在三分钟内凭记忆还原几十行配置。

4 变更前准备

4.1 配置备份

# H3C / 华为
display current-configuration > startup.cfg.bak
# Cisco
show running-config | tee /tftp/cfg-$(date +%F).txt

# 自动备份（以 telnet/ssh + expect 为例，示意）
ssh admin@10.0.0.1 "show running-config" > /backup/sw-core-$(date +%F_%H%M).cfg

备份必须落到**另一台机器**上。存在设备内部的备份，在设备起不来的时候等于没有。

4.2 检查清单

  • 确认当前无其他人在同一设备上操作
  • 确认带外管理通道可用（Console 或独立管理网）
  • 确认备用链路或冗余设备处于正常状态
  • 确认实施期间无人做关联变更
  • 确认回滚命令已经过验证（至少在一台同型号设备上试过）

5 实施步骤

以交换机 ACL 变更为例。原则是：一次只改一个维度，改完立刻验证，不要连续下十条命令再一起看结果。

# 1. 进入配置模式
system-view

# 2. 先看现有 ACL，确认编号未被占用
display acl 3001

# 3. 修改时尽量用"追加 + 最后拒绝"，而不是插到中间
acl number 3001
 rule 100 permit tcp source 10.10.20.0 0.0.0.255 destination 10.10.30.10 0
 rule 900 deny ip

# 4. 每次改动后立刻保存
save force

为什么不建议在已有规则中间插入新规则：多数设备按顺序匹配，插入会导致后续序号整体偏移，原有规则的实际生效顺序变了，而配置文件里看起来"只是多了一条"。

5.1 涉及远程操作时的自保

# 先设置一个自动回滚定时器，10 分钟不确认就还原
# 各厂商命令不同，思路一致
schedule reboot at 23:50    # 兜底：到点重启回默认配置（谨慎使用）
# 或使用 commit-confirmed（Juniper / 部分华为）
commit confirmed 10

如果设备支持"确认式提交"，一定用它。改错了没确认，设备会自动回滚，这是唯一能救回远程失联的手段。

6 回滚方案

回滚要写成可以直接粘贴的命令序列，而不是描述。

# 回滚：删除本次新增的规则
system-view
acl number 3001
 undo rule 100
 quit
save force

# 或整段恢复备份（注意会覆盖其他变更）
tftp 10.0.0.200 get cfg-2026-11-14_2130.cfg startup.cfg
reboot

整段恢复的风险是会把别人在备份之后做的变更一起冲掉。所以回滚优先用"逐条 undo"，整段恢复只在设备配置已完全混乱时使用。

7 变更后验证

验证项 方法 通过标准
配置生效 display current-configuration 对比 与变更单一致
连通性 从业务网段 ping / telnet 目标 与变更前一致
路由表 display ip routing-table 无意外路由消失
端口状态 display interface brief 无端口意外 down
业务验证 业务方实际访问 业务方书面确认

最后一项不能省。技术上通不代表业务上通，反过来也成立。让业务方点一下，比看一百行 show 命令有用。

8 记录与归档

变更单在实施完成后 24 小时内归档，附上：改前配置、改后配置、验证截图、实际耗时。如果中途有偏差（比如原计划改 3 条实际改了 5 条），在备注里写清楚原因。

归档不是为了应付检查。半年后同一台设备再出问题，这些记录是唯一能还原"当时为什么这么配"的材料。

9 常见事故与复盘要点

事故类型 典型原因 复盘该问什么
远程失联 改管理网 ACL 未保留自身来源 为什么没用确认式提交
业务中断 ACL 顺序导致默认拒绝提前命中 变更前有没有在测试设备验证
环路 STP 未开启或优先级配置错误 接入层是否统一了 STP 策略
回滚失败 备份文件不完整或缺依赖 备份是否在另一台机器上、是否验证过

复盘要追问流程，而不是追问人。"谁改的"没有价值，"为什么这个环节没拦住"才有。
